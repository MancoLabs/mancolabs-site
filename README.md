# mancolabs-site

The website for **Manco Labs LLC**: affordable, practical software help for local businesses in Shreveport-Bossier. Plain HTML and CSS, built with Vite. A 3D layer (three.js) is added on top as progressive enhancement, and the site works fully without it.

> **Status:** redesign in progress on the `redesign` branch. Stages 1 to 5 are done. Stage 6 (the final performance and accessibility pass) is next.

---

## Quick start

```bash
npm install
npm run dev        # local dev server at http://localhost:5173
npm run build      # checks copy, then builds to dist/
npm run preview    # serves dist/ at http://localhost:4173
```

Node 22.12 or newer.

| Script | What it does |
|---|---|
| `npm run dev` | Dev server with live reload (partials included) |
| `npm run build` | Runs the copy check, then the production build |
| `npm run preview` | Serves the production build |
| `npm run check:copy` | Fails if site copy contains em or en dashes |
| `npm run screenshots` | Recaptures the work screenshots from the live sites (uses your installed Chrome) |
| `npm run posters` | Rebuilds the site, then renders the hero posters and `public/og.jpg` from the real 3D scene |

### HTML directives

`vite.config.js` expands two comments in every page before Vite builds it:

- `<!-- @include header.html -->` inlines `partials/header.html`.
- `<!-- @picture src="work/werla/live-desktop" widths="480,800,1280" sizes="..." alt="..." width="1440" height="900" -->` becomes a `<picture>` with AVIF and WebP versions from `src/assets/`. Extra attributes (`width`, `height`, `loading`, `fetchpriority`, `class`) go on the `<img>`. Images lazy-load unless you pass `loading="eager"`.

## Editing content

### Services

All services live in `index.html` inside `<section id="services">`, as plain HTML:

- **Fix, Build, Automate**: each is an `<li class="stage">` with a title, a `<ul class="prices">`, one sentence, and a checklist. The picture next to each one is decorative.
- **Free consultation** and **Website care plan**: the two `<article class="extra">` cards below.

Change prices by editing the `<li>` inside `<ul class="prices">`. Write "$50 an hour", not "$50/hr", so it reads well aloud.

Each stage row is at least 82% of the screen tall on desktop. That gives the 3D laptop room to stay in place while the text beside it explains the service. The three rows stay in normal reading order, so nothing is ever hidden from screen readers or keyboard users.

### Work cards

In `index.html`, inside `<section id="work">`. There's a commented-out card template at the end of the list. For a new project:

1. Add the site to `SHOTS` in `scripts/capture-screenshots.mjs` and run `npm run screenshots`.
2. Copy the card template, fill it in, and give it an honest role label.
3. Copy `work/werla/` to `work/<slug>/` and edit it.
4. Add the page to `PAGES` in `vite.config.js` and to `public/sitemap.xml`.
5. Update the "Next project" links at the bottom of the case studies so they still form a loop.
6. Keep the View Transition names in step. On the card, the `.work-thumb` and the `<h3>` have `style="view-transition-name: shot-SLUG"` and `title-SLUG`. On the case study, the `.browser` frame and the `<h1>` use the same two names. That's what makes the card grow into the page in Chrome, Edge, and Safari. Each name must be unique on its page.

Cards tilt slightly toward the mouse and show a soft highlight (`src/work/tilt.js`). This is skipped on touch screens and with reduced motion.

### Before/after slider

`src/work/before-after.js` provides an accessible comparison slider. A real range input sits over the two images, so it works with a keyboard (arrow keys), a screen reader, a mouse, and touch. No page uses it right now, because WERLA has no faithful "before" images. To use it, copy the commented `BEFORE/AFTER` snippet from the card template in `index.html` into a case study and point it at real screenshots. The script loads only on pages that contain `[data-before-after]`.

### Screenshots

`npm run screenshots` opens each live site in Chrome at desktop (1440 wide; minicine uses 1100 because its layout is fixed-width) and phone (390 wide) sizes, then writes AVIF and WebP files to `src/assets/work/<slug>/`. Run `npm run screenshots -- werla` to redo just one.

### About photo

`src/assets/about/ethan-{300,480}.{avif,webp}` is a 4:5 head-and-shoulders crop of the original, which lives in `source-images/` (gitignored, so the uncropped photo is never committed or published). The crop ends where the backpack straps start. To redo it:

```bash
node -e "const s=require('sharp');s('source-images/ethan.jpg').extract({left:313,top:262,width:493,height:616}).toBuffer().then(b=>Promise.all([300,480].flatMap(w=>[s(b).resize({width:w}).avif({quality:60}).toFile('src/assets/about/ethan-'+w+'.avif'),s(b).resize({width:w}).webp({quality:80}).toFile('src/assets/about/ethan-'+w+'.webp')])))"
```

### WERLA

WERLA has no before/after slider. Every Wayback Machine capture of werla.net from before July 2026 is missing the old site's navigation and layout stylesheets, so none of them shows what the site really looked like.

### Copy rules

- No em dashes or en dashes. `npm run build` refuses to build if any slip in.
- No made-up testimonials, numbers, logos, or client claims.
- Short sentences, plain words.

## Colors

The brand palette in `src/styles/tokens.css` is unchanged from the original site. Never add new colors. Components use **roles** instead of palette colors directly, so every pairing passes WCAG AA:

| Role | Light | Dark | Use |
|---|---|---|---|
| `--text` | ink | paper | Body text, headings |
| `--text-2` | accent-deep (4.85:1) | paper-3 | Secondary text, labels |
| `--text-display` | ink-soft (3.61:1) | accent | **Large text only** (24px+, or 19px+ bold) |
| `--accent-text` | accent-deep | accent | Small green text: prices, role labels |
| `--field-border` | ink-soft | ink-faint | Form field outlines (3:1 rule for controls) |
| `--focus` | accent-deep | accent | Keyboard focus rings |
| `--deco` | accent | accent | Lines and icons, never text |

- **`.dark`:** a section with this class (About) uses the dark roles. The whole site switches to them when the visitor's device is in dark mode.
- **`.on-band`:** an element on the tinted `--band` background (the two service cards) gets this class so its secondary text stays readable.

## The 3D layer

The hero's floating paperwork and the laptop it assembles into are decoration on top of a page that already works. Every word, price, and link is plain HTML. The canvas is `aria-hidden`, and nothing depends on it.

### How it loads

1. **First paint:** the HTML and a static poster image of the scene. The poster is about 10 KB on phones and 24 KB on desktop.
2. **Before first paint:** an inline script in `partials/head.html` decides whether this device should even try. It sets `data-3d` on `<html>` to `pending` or `off`.
3. **After load, once the browser is idle:** `src/main.js` imports `src/three/boot.js` (2 KB) and GSAP (39 KB).
4. **GPU check:** `boot.js` checks for a real GPU, then starts the renderer:
   - in a **Web Worker** with an OffscreenCanvas when the browser supports it (Chrome, Edge, Firefox, Safari 16.4+), so three.js never blocks the page;
   - on the **main thread** otherwise.
   The renderer bundle is about 200 KB compressed.
5. **Crossfade:** after three frames render, `data-3d` becomes `live` and the canvas crossfades in over the poster.

Layout is identical in every state. The laptop is always fitted inside a page box that holds a matching drawing in poster mode. Switching modes never moves anything on the page.

### The laptop's path

`frameState()` in `boot.js` works out, every frame, which box the laptop should fill and how far each stage has progressed. The page marks three boxes:

1. **`[data-anchor="assembly"]`:** where the papers assemble into the laptop. Progress is scrubbed to scroll with GSAP ScrollTrigger.
2. **`[data-anchor="story"]`:** the Fix / Build / Automate rows.
   - **Desktop:** the laptop is held in the middle of the right-hand column while the rows scroll past.
   - **Phones:** it stays at the top of the screen, and the text fades as it slides up underneath, so the two never overlap.
   - **Effects:** the screen glitches and repairs (Fix), interface pieces fly in and snap into place (Build), and four tool icons link up into a network with data pulses along the links (Automate).
3. **`[data-anchor="check"]`:** the website check. The screen shows the visitor's site.

**Between the boxes:**
- **Desktop:** the laptop glides, and it shrinks while passing behind the two service cards.
- **Phones:** it moves only while both ends are off screen.

### When the poster stays

| Condition | Decided |
|---|---|
| `prefers-reduced-motion: reduce` | before first paint |
| Data Saver on, or a 2G connection | before first paint |
| Under 4 GB memory or under 4 CPU cores (Chromium only; Safari doesn't report these) | before first paint |
| No WebGPU and no hardware WebGL 2, or a software renderer (SwiftShader, llvmpipe) | after load |
| Renderer error, or no first frame within 15 seconds | after load |
| Frame rate under 30 fps after warm-up, even at the lowest resolution | while running: fades back to the poster and frees the GPU |

### While it runs

- **Pausing:** rendering stops when the hero and the assembly are off screen, or when the tab is hidden.
- **Resolution:** pixel ratio is capped at 2 (1.5 on touch devices). It drops in 0.25 steps if frames run long.
- **Draw calls:** all papers are a single instanced mesh. Their flutter and shading run in TSL shaders, and their positions are computed in the worker.
- **Colors:** every color comes from the CSS variables, read at runtime by `src/three/palette.js`. The paper artwork and the laptop screen are drawn from those colors (`textures.js`), so there are no image downloads. Switching the device to dark mode repaints the scene.
- **Pointer:** a mouse or trackpad gently pushes nearby papers aside, and they drift back.
- **Tilt:** on phones, a "Tilt to play" button asks for motion permission. Nothing reads the motion sensors until the visitor taps it.

### Files

| File | Role |
|---|---|
| `src/three/boot.js` | Main thread: GPU check, worker or fallback, scroll/pointer/resize/palette messages, poster fallback |
| `src/three/stage.js` | Renderer, camera, render loop, resolution watchdog. Runs in the worker or on the main thread |
| `src/three/worker.js` | Worker entry point (four lines) |
| `src/three/hero-scene.js` | Paper field, laptop, the scroll-driven assembly, the services story, and the check screen |
| `src/three/lost-scene.js` | The 404 page's floating paper |
| `src/three/about-backdrop.js` | The About section's shader background (its own canvas) |
| `src/three/textures.js` | Paper and screen artwork, drawn from the palette |
| `src/three/palette.js` | Resolves the CSS color variables to hex |

### Testing switches

Add these to the URL:

| Switch | Effect |
|---|---|
| `?3d=off` | Force the poster |
| `?3d=on` | Skip the device checks (the GPU check still runs) |
| `?3d=force-webgl` | Use the WebGL 2 backend instead of WebGPU |
| `?mainthread` | Render on the main thread instead of a worker |
| `?poster` / `?og` | Frozen frames used by `npm run posters` |

The console says why whenever it falls back to the poster.

The developer view (stage 5) asks for live numbers with `dispatchEvent(new CustomEvent('stage:want-stats', { detail: true }))`. Results arrive as `stage:stats` events, about every 2 seconds while rendering.

### Regenerating the posters

Run `npm run posters` after you change the hero text, the hero layout, the colors, or the scene. It needs Chrome with a working GPU. It renders light and dark versions at desktop and phone shapes, plus `public/og.jpg` (the social share image), and rewrites `partials/hero-poster.html`.

## Motion and small extras

| What | Where | Notes |
|---|---|---|
| Headline reveals | `src/anim/motion.js` | Section headings slide up line by line (GSAP SplitText) as they scroll in. Screen readers still get the whole heading. The hero headline uses a CSS-only entrance so it's never delayed. Headings already on screen when the script loads are left alone. |
| Magnetic buttons | `src/anim/motion.js` | Any element with `data-magnetic` leans toward the mouse. Mouse and trackpad only. |
| Scroll progress | `.scroll-progress` in `partials/header.html` | A 2px bar under the header. Driven by CSS scroll timelines where supported, and by a tiny scroll listener elsewhere (Firefox). |
| About background | `src/three/about-backdrop.js` | Slow noise in the palette's dark greens with a soft glow near the cursor. It has its own canvas inside the section, rendered by the same worker. It's capped so the section's smallest text keeps at least 4.5:1 contrast. |
| Developer view | `src/devview.js` | Konami code (up, up, down, down, left, right, left, right, B, A): 12-column grid, labeled component outlines, and live stats (page FPS, renderer and thread, 3D FPS, draw calls, pixel ratio, LCP, CLS). Escape closes it. Loads only when triggered. |
| 404 | `404.html`, `src/three/lost-scene.js` | One lost invoice floats over the page. Push it with the mouse, or tap near it on a phone, and it bounces off the screen edges. In poster mode it's a drawing. |

`src/anim/motion.js` loads after the page is idle, and never with reduced motion.

## Fonts

Inter (variable) and DM Sans 400/500, Latin subsets, self-hosted in `public/fonts/` under the SIL Open Font License. `fonts.css` also defines Arial-based fallbacks tuned to each font's measurements, so the page doesn't jump when the fonts load. Font files are cached as immutable (`public/_headers`), so rename the file if you ever replace one.

## Contact form

The contact form posts to Web3Forms, the same as before. JS sends the fields as JSON and shows the result inline. Without JS, the form falls back to a normal POST. The access key in the HTML is meant to be public.

## PageSpeed API key (for the Free Website Check, stage 4)

1. In Google Cloud Console, create or choose a project and enable the **PageSpeed Insights API**.
2. Go to **APIs & Services > Credentials > Create credentials > API key**.
3. Under **Application restrictions**, choose **Websites** and add:
   - `https://mancolabs.dev/*`
   - `http://localhost:5173/*` and `http://localhost:4173/*` (local dev and preview)
   - your Cloudflare Pages preview domain, if you want previews to work (for example `https://*.<project>.pages.dev/*`)
4. Under **API restrictions**, restrict the key to the PageSpeed Insights API only.
5. Copy `.env.example` to `.env.local` and set `VITE_PSI_API_KEY`.
6. Add the same variable in Cloudflare Pages: **Settings > Environment variables**, for Production and Preview.

Vite bakes this key into the public JavaScript, so anyone can read it. The website restrictions are what stop others from using it. Keep `Referrer-Policy: strict-origin-when-cross-origin` in `public/_headers`: stricter policies stop sending the referrer that Google checks.

## Free Website Check

A visitor types an address. The page runs Google PageSpeed Insights (v5, mobile, all four categories) straight from the browser and shows:
- four score rings, each with its number and a word ("Good", "Needs work", "Poor");
- the top three issues in plain English;
- a "Want these fixed? Free consultation." button. It fills in the contact form with the address, scores, and issues, then moves to it.

**Files:**

| File | Role |
|---|---|
| `src/check/psi.js` | Cleans up the address, calls the API (90-second timeout), and turns failures into friendly error types |
| `src/check/issues.js` | The plain-English dictionary and the ranking that picks the top three |
| `src/check/check.js` | Form, progress, results, prefill, and the laptop screen |

**How the top three are picked:** each failing audit gets a rough "points it costs you" estimate. For performance metrics that's the metric's weight. For speed fixes it comes from Google's estimated time and size savings. For everything else it's the audit's share of its category. Related audits share a family (for example, all the image ones), and only the biggest of each family is shown. No AI is involved, so nothing is made up.

**Editing the wording:** each entry in `ENTRIES` (in `issues.js`) is keyed by the Lighthouse audit id and has:
- a `title`, the headline;
- a `body`, one or two short sentences;
- a `family`.

Titles and bodies can use the audit's numbers (see the `kb`, `ms`, and `secs` helpers). An audit with no entry falls back to Google's own title, but only when there aren't three explained issues to show.

**Behavior worth knowing:**
- **Bad input:** addresses without `https://` are fine. Local network addresses get a clear "Google can't reach that" message.
- **Errors:** rate limits, unreachable sites, Google errors, timeouts, no connection, and a rejected key each get a friendly message. A rejected key also logs a console warning.
- **One check at a time:** results are cached in the visitor's browser session for 30 minutes, which saves API quota when people re-check.
- **Screen readers:** they hear when a check starts and finishes. Focus moves to the results heading, and each score ring is read as text (for example, "Performance: 52 out of 100, needs work.").
- **Laptop screen:** the screen shows a phone-shaped preview. While the test runs, it shows the visitor's domain with a scanning light. After, it replays the page's real loading frames, then shows the final screenshot. This works in 3D and in poster mode.
- **Without JavaScript:** the form opens Google's own PageSpeed report in a new tab.
- **Testing from your phone on your network:** add your computer's address (for example, `http://192.168.1.92:4173/*`) to the key's allowed websites in Google Cloud.
