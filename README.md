# mancolabs-site

The website for **Manco Labs LLC**: affordable, practical software help for local businesses in Shreveport-Bossier. Plain HTML and CSS, built with Vite. A 3D layer (three.js) is added on top as progressive enhancement, and the site works fully without it.

> **Status:** the redesign is complete on the `redesign` branch and ready to launch. See the launch checklist under "Deploying".

## Results

These are Lighthouse 13.5 results on the production build (`npm run build && npm run preview`), measured on October 11, 2026. Mobile runs simulate a mid-range phone on slow 4G. The home page was measured with the 3D running (a real GPU) and again with the GPU disabled, which is the poster path.

| Page | Mobile perf | Desktop perf | Accessibility | Best practices | SEO | Mobile LCP | TBT | CLS |
|---|---|---|---|---|---|---|---|---|
| Home, 3D (median of 3) | 99 | 100 | 100 | 100 | 100 | 1.95 s | 0 ms | 0 |
| Home, poster path | 100 | 100 | 100 | 100 | 100 | 1.66 s | 0 ms | 0 |
| Case studies (each) | 99 | 100 | 100 | 100 | 100 | 2.0 s | 0 ms | 0 |
| 404 | 100 | 100 | 100 | 100 | 63* | 1.66 s | 0 ms | 0 |

\* The 404 is `noindex` on purpose, so search engines don't list "not found" pages. Lighthouse counts that against SEO.

**Why mobile performance is 99, not 100:** the hero keeps animating after it fades in, so Speed Index never sees a "finished" page (2.4 s with 3D, 1.2 s without). That's the cost of a live hero.

**Also checked:**
- **axe-core (WCAG 2.0/2.1 A and AA):** zero violations on every page, in light and dark mode, at desktop and phone sizes.
- **Keyboard:** a full walk through the home page found 33 stops in a logical order. Each has a visible focus ring and scrolls fully into view.
- **Reflow:** no sideways scrolling at 320px wide or at 200% zoom.
- **Headings:** one h1 per page and no skipped levels.
- **Browsers:** Chrome, Firefox, and WebKit run every page with no console errors. Real Safari and iPhone checks are in the launch checklist.

**Tried and rejected:** inlining the CSS into each page. It made first paint slower (1.2 s to 1.4 s on simulated slow 4G), because the bigger HTML cost more than the separate request saved.

**Compressed sizes (brotli):**
- **First paint on a phone:** HTML 8 KB, CSS 7 KB, JS 2 KB, fonts 61 KB, poster 10 to 24 KB.
- **After idle, capable devices only:** the 3D renderer is about 204 KB, and GSAP is 39 KB.
- **Website check:** 8 KB.

### HTML directives

`vite.config.js` expands two comments in every page before Vite builds it:

- `<!-- @include header.html -->` inlines `partials/header.html`.
- `<!-- @picture src="work/werla/live-desktop" widths="480,800,1280" sizes="..." alt="..." width="1440" height="900" -->` becomes a `<picture>` with AVIF and WebP versions from `src/assets/`. Extra attributes (`width`, `height`, `loading`, `fetchpriority`, `class`) go on the `<img>`. Images lazy-load unless you pass `loading="eager"`.

## Editing content

### Services

All services live in `index.html` inside `<section id="services">`, as plain HTML:

- **Fix, Build, Automate**: each is an `<li class="stage">` with a title, a `<ul class="prices">`, one sentence, and a checklist. The picture next to each one is decorative.
- **Free consultation** and **Website care plan**: the two `<article class="extra">` cards below.

Change prices by editing the `<li>` inside `<ul class="prices">`. Write "$50 an hour", not "$50/hr", so it reads well aloud.

Each stage row is at least 82% of the screen tall on desktop. That gives the 3D laptop room to stay in place while the text beside it explains the service. The three rows stay in normal reading order, so nothing is ever hidden from screen readers or keyboard users.

### Work cards

In `index.html`, inside `<section id="work">`. There's a commented-out card template at the end of the list. For a new project:

1. Add the site to `SHOTS` in `scripts/capture-screenshots.mjs` and run `npm run screenshots`.
2. Copy the card template, fill it in, and give it an honest role label.
3. Copy `work/werla/` to `work/<slug>/` and edit it.
4. Add the page to `PAGES` in `vite.config.js` and to `public/sitemap.xml`.
5. Update the "Next project" links at the bottom of the case studies so they still form a loop.
6. Keep the View Transition names in step. On the card, the `.work-thumb` and the `<h3>` have `style="view-transition-name: shot-SLUG"` and `title-SLUG`. On the case study, the `.browser` frame and the `<h1>` use the same two names. That's what makes the card grow into the page in Chrome, Edge, and Safari. Each name must be unique on its page.

Cards tilt slightly toward the mouse and show a soft highlight (`src/work/tilt.js`). This is skipped on touch screens and with reduced motion.

## The 3D layer

The hero's floating paperwork and the laptop it assembles into are decoration on top of a page that already works. Every word, price, and link is plain HTML. The canvas is `aria-hidden`, and nothing depends on it.

### How it loads

1. **First paint:** the HTML and a static poster image of the scene. Desktop gets a full-hero poster (about 24 KB). Phones get a small poster of just the paper band (a few KB), and never download the desktop one.
2. **Before first paint:** an inline script in `partials/head.html` decides whether this device should even try. It sets `data-3d` on `<html>` to `pending` or `off`.
3. **After load, once the browser is idle:** `src/main.js` imports `src/three/boot.js` (2 KB) and GSAP (39 KB).
4. **GPU check:** `boot.js` checks for a real GPU, then starts the renderer:
   - **Web Worker, WebGL 2 (the default).** Used whenever the browser can hand a canvas to a worker (Chrome, Edge, Firefox, Safari 16.4+), so three.js never blocks the page. WebGPU inside a worker caused scroll stutter on some machines, so the worker always uses WebGL 2. It looks identical.
   - **Main thread, WebGPU if available, otherwise WebGL 2.** Used by browsers that can't hand a canvas to a worker.
   The renderer bundle is about 200 KB compressed.
5. **Warm-up:** before the first visible frame, every shader is compiled, every texture uploaded, and the whole scene drawn once while the canvas is still invisible. That includes parts that start off screen and only appear later (the laptop, the services effects), so nothing has to be set up in the middle of a scroll. The live scene replaces the poster only after 12 smooth frames in a row (each under 25 ms). It then crossfades in over 600 ms. If it can't get smooth within 5 seconds, the poster stays.
6. **Pausing:** rendering stops when the 3D parts of the page are off screen or the tab is hidden. The scene and everything on the GPU stay loaded, so it resumes on the next frame with no warm-up or crossfade.

Layout is identical in every state. The laptop is always fitted inside a page box that holds a matching drawing in poster mode. Switching modes never moves anything on the page.

### The laptop's path

On desktop and tablets, `frameState()` in `boot.js` works out, every frame, which box the laptop should fill and how far each stage has progressed. Phones work differently (see "Phones: the canvas scrolls with the page" below). The page marks three boxes:

1. **`[data-anchor="assembly"]`:** where the papers assemble into the laptop. On desktop, progress is scrubbed to scroll with GSAP ScrollTrigger. On touch devices it plays on its own over about 1.3 seconds and plays in reverse if you scroll back. Tablets start it once the laptop box is about a third into view; phones start it once the paper band has scrolled out of view. Scroll-scrubbing stutters with touch momentum scrolling. The Fix, Build, and Automate effects work the same way on touch devices: each plays through when its row reaches the reading area.
2. **`[data-anchor="story"]`:** the Fix / Build / Automate rows.
   - **Desktop:** the laptop is held in the middle of the right-hand column while the rows scroll past.
   - **Phones:** it stays at the top of the screen (held by `position: sticky`), and the text fades as it slides up underneath, so the two never overlap.
   - **Effects:** the screen glitches and repairs (Fix), interface pieces fly in and snap into place (Build), and four tool icons link up into a network with data pulses along the links (Automate).
3. **`[data-anchor="check"]`:** the website check. The screen shows the visitor's site. On phones the laptop opens when its box comes into view.

**Between the boxes:**
- **Desktop:** the laptop glides, and it shrinks while passing behind the two service cards.
- **Phones:** it moves only while both ends are off screen.

### Phones: the canvas scrolls with the page

A phone scrolls the page on its own thread, separately from JavaScript. Anything the 3D moves to follow the scroll is drawn a frame or more late, so it lags and jitters against the page. So on phones (touch screen and narrower than 700px), nothing in the 3D follows the scroll position. `prepareFlow()` in `boot.js` sets this up:

- **One canvas inside the page, not fixed to the screen.** It covers the hero's paper band down to the laptop box, so the papers really fly from the band into the laptop, all inside one canvas.
- **A sticky holder.** The canvas sits in `.flow-pin`, a zero-height `position: sticky` box at the top of a wrapper (`.flow-run`) around the services heading and rows. The browser carries it up with the page, holds the laptop 84px from the top while the rows scroll underneath, and lets go where the rows end. The wrapper and holder are added by JavaScript and take no room, so the layout is identical with or without them.
- **The website check.** Halfway between the end of the rows and the check box, while both are off screen, the canvas moves into `[data-anchor="check"]`.
- **Only timed animations inside:** the assembly, the services effects, the scanning light, and the laptop opening at the check.
- **The camera.** Each canvas is a fixed window onto a virtual screen (`Stage.applyFlow`). As the papers fly, the window slides from the band's view to the pinned laptop's view, so each looks the way it did on the old full-screen canvas. That is also why the existing band posters still line up.
- **Rotation.** If the page switches to the wide layout (for example, turning the phone sideways), the 3D gives way to the drawings for the rest of the visit.

Tablets and desktop keep the full-screen canvas.

### When the poster stays

| Condition | Decided |
|---|---|
| `prefers-reduced-motion: reduce` | before first paint |
| Firefox on phones, iOS and Android (its toolbar resizes the page as it slides, which blanked and redrew the canvas) | before first paint |
| Data Saver on, or a 2G connection | before first paint |
| Under 4 GB memory or under 4 CPU cores (Chromium only; Safari doesn't report these) | before first paint |
| No WebGPU and no hardware WebGL 2, or a software renderer (SwiftShader, llvmpipe) | after load |
| Renderer error, or no first frame within 15 seconds | after load |
| Frame rate under 30 fps after warm-up, even at the lowest resolution | while running: fades back to the poster and frees the GPU |

### While it runs

- **Pausing:** rendering stops when the hero and the assembly are off screen (on phones, when the canvas is), or when the tab is hidden.
- **Resolution:** pixel ratio is capped at 2 (1.5 on touch devices). It drops in 0.25 steps if frames run long.
- **Draw calls:** all papers are a single instanced mesh. Their flutter and shading run in TSL shaders, and their positions are computed in the worker.
- **Colors:** every color comes from the CSS variables, read at runtime by `src/three/palette.js`. The paper artwork and the laptop screen are drawn from those colors (`textures.js`), so there are no image downloads. Switching the device to dark mode repaints the scene.
- **Pointer:** a mouse or trackpad gently pushes nearby papers aside, and they drift back.
- **Phones:** 24 smaller papers live in their own band under the headline (`.hero-band`), fully on screen on load and never under the header or behind text. Desktop keeps 96 papers framing the text.
- **Address bar:** the phone address bar sliding in and out never re-measures anything. ScrollTrigger runs with `ignoreMobileResize`, and the 3D code uses a stable 100svh height.
- **Firefox on phones (iOS and Android):** its toolbar resizes the page while it slides (on an iPhone, the page height jumps between about 670 and 798px), which moved the page and blanked and redrew the 3D. The head script spots it from the user agent (`FxiOS` on iOS, `Android` with `Firefox/` on Android), records the height on load as `--fx-vh`, adds `.ff-mobile`, and always shows the drawings instead of the 3D. The hero and band use `--fx-vh` instead of `svh`, so the text stays still, and scroll anchoring is off. A new height is taken only when the width changes (the phone turned). With "Request desktop site" on, Firefox sends a desktop user agent and is treated like any desktop browser.

### Testing switches

Add these to the URL:

| Switch | Effect |
|---|---|
| `?3d=off` | Force the poster |
| `?3d=on` | Skip the device checks (the GPU check still runs) |
| `?3d=force-webgl` | Use WebGL 2 everywhere, including the main thread |
| `?3d=force-webgpu` | Use WebGPU inside the worker (off by default; for testing only) |
| `?mainthread` | Render on the main thread instead of a worker |
| `?poster` / `?og` | Frozen frames used by `npm run posters` |

The console says why whenever it falls back to the poster.

The developer view (stage 5) asks for live numbers with `dispatchEvent(new CustomEvent('stage:want-stats', { detail: true }))`. Results arrive as `stage:stats` events, about every 2 seconds while rendering.

### Regenerating the posters

Run `npm run posters` after you change the hero text, the hero layout, the colors, or the scene. It needs Chrome with a working GPU. It renders light and dark versions at desktop and phone shapes, plus `public/og.jpg` (the social share image), and rewrites `partials/hero-poster.html`.

## PageSpeed API key (for the Free Website Check, stage 4)

1. In Google Cloud Console, create or choose a project and enable the **PageSpeed Insights API**.
2. Go to **APIs & Services > Credentials > Create credentials > API key**.
3. Under **Application restrictions**, choose **Websites** and add:
   - `https://mancolabs.dev/*`
   - `http://localhost:5173/*` and `http://localhost:4173/*` (local dev and preview)
   - your Cloudflare Pages preview domain, if you want previews to work (for example `https://*.<project>.pages.dev/*`)
4. Under **API restrictions**, restrict the key to the PageSpeed Insights API only.
5. Copy `.env.example` to `.env.local` and set `VITE_PSI_API_KEY`.
6. Add the same variable in Cloudflare Pages: **Settings > Environment variables**, for Production and Preview.

Vite bakes this key into the public JavaScript, so anyone can read it. The website restrictions are what stop others from using it. Keep `Referrer-Policy: strict-origin-when-cross-origin` in `public/_headers`: stricter policies stop sending the referrer that Google checks.

## Free Website Check

A visitor types an address. The page runs Google PageSpeed Insights (v5, mobile, all four categories) straight from the browser and shows:
- four score rings, each with its number and a word ("Good", "Needs work", "Poor");
- the top three issues in plain English, under "Top things to fix";
- a "Want these fixed? Free consultation." button. It fills in the contact form with the address, scores, and issues, picks "Fix something" as the service, then moves to it.

Under the list, a collapsed **Accessibility details** section shows every failing automated accessibility check, in plain English and grouped by issue, with how many places on the page each one affects and up to two readable examples ("Book now", never code). It comes from the same PageSpeed result, so it costs no extra request. It ends with a note that automated tests catch only some accessibility problems and that a full review includes testing by hand.

When all four scores are 90 or above, the same list is framed as polish instead: the heading reads "Minor suggestions", a line says none of it is urgent, the button reads "Want a second opinion? Free consultation.", and the prefilled message asks for a second opinion without changing the service.

**Files:**

| File | Role |
|---|---|
| `src/check/psi.js` | Cleans up the address, calls the API (90-second timeout), and turns failures into friendly error types |
| `src/check/issues.js` | The plain-English dictionary, the ranking that picks the top three, and `a11yReport()` for the accessibility details |
| `src/check/check.js` | Form, progress, results, prefill, and the laptop screen |
| `partials/check-tool.html` | The check's markup, shared by the home page and `/tools/` |

**How the top three are picked:** each failing audit gets a rough "points it costs you" estimate. For performance metrics that's the metric's weight. For speed fixes it comes from Google's estimated time and size savings. For everything else it's the audit's share of its category. Related audits share a family (for example, all the image ones), and only the biggest of each family is shown. No AI is involved, so nothing is made up.

**Editing the wording:** each entry in `ENTRIES` (in `issues.js`) is keyed by the Lighthouse audit id and has:
- a `title`, the headline;
- a `body`, one or two short sentences;
- a `family`.

Titles and bodies can use the audit's numbers (see the `kb`, `ms`, and `secs` helpers). An audit with no entry falls back to Google's own title, but only when there aren't three explained issues to show.

Accessibility checks that rarely make the top three have their entries in `MORE_A11Y`, which only the accessibility details use, so adding to it never changes the top three. In the details, checks whose titles read the same are grouped as one issue.

**Behavior worth knowing:**
- **Bad input:** addresses without `https://` are fine. Local network addresses get a clear "Google can't reach that" message.
- **Errors:** rate limits, unreachable sites, Google errors, timeouts, no connection, and a rejected key each get a friendly message. A rejected key also logs a console warning.
- **One check at a time:** results are cached in the visitor's browser session for 30 minutes, which saves API quota when people re-check.
- **Screen readers:** they hear when a check starts and finishes. Focus moves to the results heading, and each score ring is read as text (for example, "Performance: 52 out of 100, needs work.").
- **Laptop screen:** the screen shows a phone-shaped preview. While the test runs, it shows the visitor's domain with a scanning light. After, it replays the page's real loading frames, then shows the final screenshot. This works in 3D and in poster mode.
- **Without JavaScript:** the form opens Google's own PageSpeed report in a new tab.
- **Testing from your phone on your network:** add your computer's address (for example, `http://192.168.1.92:4173/*`) to the key's allowed websites in Google Cloud.

### Email health check

The visitor types a domain (or pastes an email address or web address; only the domain is used). The page looks up public DNS records through Cloudflare's DNS-over-HTTPS JSON service, falling back to Google's if Cloudflare can't be reached. Neither needs a key, and nothing is stored.

| Record | Looked up at | Result |
|---|---|---|
| Mail servers (MX) | the domain | Names the email provider from the server names (`PROVIDERS`), or says the domain doesn't receive email |
| SPF | the domain's TXT records | Missing, more than one, allows anyone (`+all`), unfinished (no `all`, or `?all`), too long (over 10 lookups), doesn't seem to include the provider, or good |
| DMARC | `_dmarc.` + domain | Missing, has a mistake, monitoring only (`p=none`), partly on (`pct` under 100), or good (`quarantine` or `reject`) |
| DKIM | `<name>._domainkey.` + domain, for about 30 common names (`SELECTORS`) | Found (and under which name), or "not found under common names". It never says "missing": services can use a custom name nobody can guess. |

**Overall:** "Set up to stay out of the spam folder" needs a good SPF and an enforced DMARC. With neither, it's "Not set up". Anything between is "Partly set up". DKIM doesn't count against anyone, since it can't be confirmed from outside.

**SPF follows its references:** `include:` and `redirect=` are followed the way inboxes do, up to the 10-lookup limit inboxes enforce. That's how it knows whether the provider is listed somewhere down the chain, and when a list is too long to work.

**Behavior worth knowing:**
- **Bad input:** a misspelled or made-up domain gets "That domain doesn't seem to exist." Local names like `.local` are rejected.
- **The raw records** are under "Show the records we found", for anyone who wants to see exactly what was read.
- **Screen readers:** they hear when results are ready, and focus moves to the results heading.
